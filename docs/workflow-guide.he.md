# חלק א׳: תהליך העבודה במערכת

## התמונה הגדולה

חשבו על המערכת כמו על **מגדל פיקוח של נמל**: כל הגורמים בשרשרת (יצואן, יבואן, משלח בינלאומי, חברת ספנות) יושבים על אותו מסך אחד, במקום להתכתב במיילים.

**נקודה אחת שצריכה להיאמר מראש.** יגאל הוא סוחר שמקבל עמלה. הוא קונה מיצרנים ומוכר ליבואנים, ויש **מחיר אחד** ולא שניים: שווי העסקה המלא, שכולל סחורה, הובלה, ביטוח ומכס. היבואן מחויב במחיר המלא; היצרן מקבל את המחיר פחות העמלה; יגאל שומר את העמלה, ברירת המחדל שני אחוזים. העמלה יוצאת מהצד של היצרן ולא מתווספת מעל המחיר של הקונה, ולכן ליבואן אין תמריץ מחירי לעקוף אותו.

**האנלוגיה:** סוכן נסיעות שמשולם מתוך התעריף של המלון. הנוסע משלם את התעריף המלא, הסוכן שומר חלק, והמלון מקבל פחות. אף אחד לא משלם תוספת עבור הסוכן; הספק הוא זה שמממן אותו.

זרימת העבודה הבסיסית:

```
כניסה למערכת  →  הזמנה חדשה  →  מעקב אחרי המשלוח  →  מסמכים ואישורים
      →  שיתוף פעולה בין הצדדים  →  חשבונית וגבייה  →  ניתוח וביצועים
```

לפני הזרימה הזאת יושב **Deckhand**, השלב שבו מזהים מגיעים במייל וצריכים להיכנס לטופס. ראו את הסעיף הבא.

## Deckhand: להפסיק להקליד מזהים מחדש

לפני כל מה שלמטה יש שלב אחד שהמערכת לא עשתה עבורכם עד היום: מזהי משלוח ומספרי חותם מגיעים במייל, ומישהו מקליד אותם מחדש לתוך INTTRA. **Deckhand** הוא העמוד שמסיר בדיוק את ההקלדה הזאת.

השם הוא ההסבר: deckhand הוא איש הצוות הזוטר שעושה את עבודת הסיפון השגרתית כדי שהקצינים יוכלו לנווט. **Deckhand מעתיק, אתם שופטים.**

**איך משתמשים:**

1. מדביקים את גוף המייל בתיבה, או מצרפים את המסמך (הודעת הגעה, אישור הזמנה, שטר מטען, רשימת קונטיינרים) כ־PDF, JPEG או PNG, עד 5MB.
2. לוחצים **Extract**.
3. **קוראים את הבלוק מול המייל המקורי.** זה לא עיכוב, זה המוצר.
4. מעתיקים שדה־שדה, או את הבלוק כולו, לטופס.

**מה חוזר:** מספר הזמנה או משלוח, מספרי קונטיינרים, מספרי חותם צמודים לקונטיינר שלידו הם הופיעו, שם אונייה ומספר הפלגה, נמלי טעינה ופריקה, ורשימה מפורשת של כל מה ש־Deckhand לא היה בטוח בו.

**הכללים שהוא עובד לפיהם:**

- **הוא לא מנחש התאמה.** קונטיינר וחותם מחוברים זה לזה רק אם המסמך הראה אותם יחד: אותה שורה בטבלה, אותה שורת טקסט, או אותה פסקה מסומנת. הוא גם אומר לכם איזה מהשלושה. כל השאר מדווח בנפרד תחת **לא מותאם**, עם אזהרה. חותם על הקונטיינר הלא נכון גרוע יותר מאשר שום פלט.
- **חסר הוא ערך.** שדה שלא נמצא מודפס כ־missing, אף פעם לא נעלם בשקט.
- **רמת ודאות היא לכל שדה בנפרד**, לא ציון אחד כולל.
- **מספרי קונטיינר נבדקים מול ISO 6346.** ספרת ביקורת שנכשלת מסומנת בקול, ולעולם לא מתוקנת בשקט. למספרי חותם אין תקן ואין ספרת ביקורת, ולכן אי אפשר לאמת אותם בכלל, והעמוד אומר את זה.
- **שום דבר לא נשמר.** Deckhand קורא, מחזיר, ושוכח. הוא לא קורא מבסיס הנתונים ולא כותב אליו.
- **לעולם לא סיסמאות פורטל.** Deckhand לא מתחבר ל־INTTRA, ל־ACE או ל־Login.gov, ולא יתחבר. הוא מגיש לכם טקסט; אתם מפעילים את הפורטל.

**הרשאות:** משתמשי `admin` ו־`ops` של הארגון הפנימי בלבד. אם לא הוגדר מפתח לשירות החילוץ בפריסה (`ANTHROPIC_API_KEY`), Deckhand נופל לקורא דטרמיניסטי שמטפל בטקסט בלבד, וקבצי PDF ותמונות יחזירו הודעה שמבקשת להדביק את הטקסט במקום.

## שלב 0: מי אתם במערכת

לכל משתמש יש **שני מאפיינים** שקובעים מה הוא רואה ומה הוא רשאי לעשות:

**1. תפקיד (Role), מה מותר לעשות:**

| תפקיד | מה מותר |
|---|---|
| `admin` (מנהל) | הכול, כולל ניהול משתמשים והגדרת אינטגרציות |
| `ops` (תפעול) | להזמין, לאשר מסמכים, להגיב, למשוך חשבוניות |
| `viewer` (צופה) | צפייה בלבד |

**2. ארגון (Organization), מה רואים:**

| סוג ארגון | מה רואים |
|---|---|
| `internal` (Tidelane) | את כל המשלוחים ברשת |
| `shipper` (יצואן) | רק משלוחים שהם צד בהם |
| `forwarder` (משלח) | רק משלוחים שהם משלחים |
| `consignee` (יבואן) | רק המשלוחים הנכנסים אליהם |
| `carrier` (מוביל ימי) | רק משלוחים שהם מובילים |

האנלוגיה: **התפקיד הוא המפתח, הארגון הוא הקומה בבניין.** גם מנהל של ארגון שותף לא יראה משלוח שהוא לא צד בו, וגם משתמש פנימי בתפקיד צופה לא יוכל לאשר מסמך.

**חשוב:** ההרשאות נאכפות בשרת (ב־API), לא רק במסך. גם גישה ישירה דרך כתובת URL תיחסם.

**3. בידוד בין הצדדים המסחריים.** על גבי כל זה יש כלל נוסף: משתמש של ארגון שותף רואה את השורות של הארגון שלו עצמו, ואת נותני השירות (משלח ומוביל ימי), ולעולם לא ארגון אחר בתפקיד מסחרי. הסיבה היא בדיוק העסק של יגאל: היצרן שממנו קנה והיבואן שלו מכר הם שני צדדים על אותו משלוח, ורשימת הספקים ורשימת הלקוחות הן העסק עצמו. מי שמראה לאחד את השני מוציא את הסוחר מהעסקה של עצמו. בענף קוראים לרעיון הזה **switch bill of lading**: תנועה פיזית אחת, שני סטים של ניירת במכוון.

הכלל חל גם על מי שכתב תגובה ומי שהעלה מסמך, ולא רק על לשונית הצדדים. **מה שהוא לא סוגר:** טקסט חופשי. משפט בתוך תגובה שמזכיר את הצד השני אי אפשר לסנן, ולכן צריך לסכם במפורש אם משתמשים בשרשור התגובות בין צדדים שונים או רק מול צד אחד בכל פעם.

## מודל העסק: סוחר או מפעיל

בהגדרות יש לשונית <span dir="ltr">Business model</span>, פתוחה למשתמש `admin` של הארגון הפנימי בלבד. היא בוחרת באיזה מודל כל המערכת מוצגת.

| | `trader` (ברירת מחדל) | `operator` |
|---|---|---|
| תוויות הצדדים | יצרן, יבואן | יצואן, נמען |
| הכסף על המשלוח | שווי עסקה, שיעור עמלה, עמלה, ומה שהיצרן מקבל | עלות הובלה בלבד |
| ניתוח | שווי עסקאות, עמלה שנצברה, שיעור אפקטיבי | הוצאות הובלה, עלות ממוצעת ל-TEU |
| חשבוניות | היבואן מחויב בשווי העסקה | השולח מחויב בהובלה ובתוספות |
| בידוד בין הצדדים המסחריים | פועל | **כבוי** |

**שלושה מספרים שתמיד מסתדרים.** על משלוח במודל `trader` יושבים שווי העסקה, העמלה ומה שהיצרן מקבל. השניים האחרונים **נגזרים בזמן קריאה** מהראשון ומשיעור העמלה, בדיוק כמו שמצב החשבונית נגזר; לכן שינוי של השיעור מחשב מחדש את שניהם, והם לא יכולים לסתור זה את זה. השיעור נלקח משיעור הבית, אלא אם למשלוח יש שיעור משלו.

**משלוח בלי מחיר מוסכם הוא מקרה לגיטימי.** הוא מוצג כלא מוגדר ולא כאפס, ולעולם לא מנוחש מעלות ההובלה. באשף ההזמנה השדה אופציונלי במכוון.

**אזהרה אחת, והיא היחידה מסוגה במערכת.** מעבר ל-`operator` **מכבה את בידוד הצדדים המסחריים**. במודל הזה יצואן ונמען על אותו שטר מטען כבר מכירים זה את זה, ולכן רשימת הצדדים המלאה נחשפת לכל ארגון שותף על המשלוח. זה נכון למודל הזה, וזה שגוי אם בבסיס הנתונים יושבים הספקים והלקוחות האמיתיים של סוחר. לפני שנתון אמיתי אחד נכנס צריך לוודא שהמודל קורא `trader`.

## שלב 1: כניסה ומסך הבית

נכנסים עם אימייל וסיסמה. המערכת פותחת את **Dashboard (מגדל הפיקוח)**, או כל עמוד אחר שהגדרתם כעמוד ברירת מחדל בהגדרות.

מה רואים בדשבורד:

- **מדדי KPI**: מספר משלוחים פעילים, קונטיינרים בים, עמידה בזמנים, וחשיפה כספית לדמי השהיה (Detention & Demurrage).
- **חריגים**: משלוחים שנמצאים באיחור, וצריך לטפל בהם עכשיו.
- **הגעות קרובות**: מה נוחת בנמל בימים הקרובים.
- **פיד פעילות**: אבני הדרך האחרונות שאושרו ברשת.

**כלל אצבע לעבודה יומית:** מתחילים מהחריגים, לא מרשימת כל המשלוחים.

## שלב 2: הזמנה חדשה (New Booking)

אשף בארבעה שלבים. רק `admin` ו־`ops` יכולים להזמין.

| שלב | מה ממלאים |
|---|---|
| 1. Route (מסלול) | נמל מוצא, נמל יעד, ותנאי סחר (Incoterm: FOB, CIF, EXW, DDP) |
| 2. Cargo (מטען) | סוג וכמות קונטיינרים (20DV, 40DV, 40HC, 40RF), משקל ותיאור המטען |
| 3. Schedule (הפלגה) | בוחרים הפלגה מתוך רשימה; לכל אפשרות מוצגים מחיר, זמן שיט, ופליטות CO₂ |
| 4. Review (אישור) | סיכום לפני שליחה |

בסיום נוצר משלוח אמיתי בבסיס הנתונים עם מספר הזמנה בפורמט `TL-2026-####`. הוא נשאר אחרי רענון הדף, ומשתמשים אחרים בארגון שלכם רואים אותו גם.

**האנלוגיה:** זה כמו הזמנת טיסה, אבל לקונטיינר; בוחרים מסלול, כמות מזוודות, ואז את הטיסה עצמה לפי מחיר מול זמן.

## שלב 3: מעקב אחרי המשלוח

יש שתי דרכים לעקוב:

**א. עמוד Shipments (משלוחים)**
טבלה עם חיפוש וסינון של כל המשלוחים שאתם רשאים לראות. לחיצה על שורה פותחת את **כרטיס המשלוח**, ובו:

- **מפת נמלי עגינה (Ports of call)**: מפה של המסלול עם סימון כל נמל שהאונייה אמורה לעגון בו, לפי סדר ההפלגה. הקטע שכבר הופלג מסומן בקו מלא, מה שנותר מקווקו, ונקודה כחולה מציינת את מיקום האונייה כרגע. לחיצה על נמל (או על הכרטיסייה שמתחת למפה) פותחת חלונית עם פרטי הנמל, המדינה, תפקידו במסלול (נמל טעינה, שינוע ביניים, או נמל פריקה), ה־ETA או ה־ETD, כמה ימים נותרו או עברו, וכל אבני הדרך שמתרחשות באותו נמל. צבע הסימון מבדיל בין נמל שכבר עגנו בו (ירוק), הנמל הבא (כחול), ונמל עתידי (אפור).
- **ציר אבני דרך**: מתוכנן מול בפועל, בשמונה תחנות:
  `booking_confirmed` (הזמנה אושרה) ← `container_gate_in` (כניסת קונטיינר לנמל) ← `loaded_on_vessel` (העמסה) ← `vessel_departed` (הפלגה) ← `transshipment` (שינוע ביניים) ← `vessel_arrived` (הגעה) ← `gate_out` (יציאה מהנמל) ← `delivered` (נמסר)
- **קונטיינרים**: מספר, סוג, חותם, משקל, וחשיפה לדמי השהיה בדולרים.
- **מסמכים**: ראו שלב 4.
- **צדדים**: מי היצואן, היבואן, המשלח והמוביל, כולל איש קשר.
- **שרשור הערות**: ראו שלב 5.

סטטוסים אפשריים של משלוח: `booking_confirmed`, `awaiting_departure`, `in_transit`, `transshipment`, `arrived`, `delivered`, `delayed`.

**ב. עמוד Track & Trace (מפה)**
מפת עולם עם האוניות שנמצאות כרגע בים, מצוירות על נתיבי סחר אמיתיים (סואץ, מיצרי מלאקה, טרנס־פסיפיק). לחיצה על אונייה מדגישה את המסלול שלה. הצבעים מבחינים בין בדרך, שינוע ביניים, ואיחור.

## שלב 4: מסמכים ואישורים

עמוד **Documents** הוא מרשם חוצה־משלוחים של כל המסמכים.

סוגי מסמכים: `SI` (הוראות שילוח), `BL` (שטר מטען), `VGM` (הצהרת משקל מאומת), `COMMERCIAL_INVOICE` (חשבונית מסחרית), `PACKING_LIST` (רשימת אריזה).

מצבי מסמך: `draft` (טיוטה) ← `pending_approval` (ממתין לאישור) ← `approved` (אושר).

**תהליך העבודה:** מסמך שממתין לאישור מסומן בכרטיס המשלוח. משתמש `ops` או `admin` לוחץ אישור, והאישור נשמר בבסיס הנתונים ונשאר אחרי רענון. משתמש `viewer` יראה את המסמך אבל לא יוכל לאשר.

## שלב 5: שיתוף פעולה בין הצדדים

בכל כרטיס משלוח יש שרשור הערות משותף. במקום שרשור מיילים בין ארבע חברות, ההתכתבות יושבת על המשלוח עצמו, ולכן היא נשארת בהקשר ונגישה לכל מי שרשאי לראות את המשלוח. משתמשי `ops` ו־`admin` יכולים לכתוב, `viewer` רק לקרוא.

## שלב 6: חשבוניות (QuickBooks)

עמוד **Invoices** מציג את החשבוניות שנמשכו מ־QuickBooks Online. זהו עמוד פנימי בלבד: רק משתמשי `admin` ו־`ops` של הארגון הפנימי (Tidelane). ארגונים שותפים לא רואים נתונים פיננסיים בכלל.

- כל חשבונית מקושרת אוטומטית למשלוח שהיא מחייבת, לפי מספר ההזמנה (`TL-2026-####`) שנמצא במספר המסמך, בהערה או בשורות החשבונית.
- הסטטוס מחושב בזמן קריאה: `open` (פתוחה), `overdue` (באיחור), `paid` (שולמה), `void` (בוטלה).
- לחיצה על **משיכה מ־QuickBooks** מסנכרנת מחדש; חשבוניות קיימות מתעדכנות ולא משוכפלות.
- כל עוד לא חוברה חברה אמיתית ב־QuickBooks, המערכת עובדת במצב Mock עם נתונים קבועים ועקביים.

## שלב 7: ניתוח וביצועים (Analytics)

מחושב בזמן אמת מהמשלוחים שאתם רשאים לראות:

- נפח TEU לפי חודש
- חלוקה בין מובילים ימיים
- עמידה בזמנים מול יעד של 90%
- פליטות CO₂ לפי נתיב סחר

## שלב 8: הגדרות (Settings)

- **פרופיל**: שם ותפקיד.
- **העדפות**: אזור זמן, פורמט תאריך, עמוד ברירת מחדל, והתראות. נשמר לכל משתמש בנפרד.
- **משתמשים** (מנהל בלבד): הזמנת משתמש, שינוי תפקיד או ארגון, השבתה.
- **אינטגרציות** (מנהל בלבד): שלושה מחברים חיצוניים, ראו למטה.

## האינטגרציות בקצרה

| מחבר | למה הוא משמש | מצב היום |
|---|---|---|
| CBP ACE | מכס אמריקאי: סטטוס ISF 10+2, כניסה ושחרור | להשאיר ב־Mock עד שיחוברו מפרטי הספק |
| E2open INTTRA | לוחות הפלגות לאשף ההזמנה | להשאיר ב־Mock |

לכל מחבר יש מתג הפעלה, בחירה בין **Mock** (נתוני הדגמה) ל־**Live** (חיבור אמיתי), שדות אישורי גישה, וכפתור **Test connection**. המפתחות מוצפנים לפני שהם נשמרים ולעולם לא מוחזרים מה־API, אלא רק ארבע הספרות האחרונות. מחבר מושבת מחזיר שגיאת 503 בנקודות הקצה שלו.

**חיבור QuickBooks, שתי דרכים:**
1. **Sign in with Intuit** (מומלץ): שומרים כתובת בסיס, Client ID ו־Client Secret, רושמים את כתובת ה־callback שמוצגת בכרטיס אצל Intuit, ולוחצים **Connect to QuickBooks**.
2. **הדבקת ערכים**: מוציאים Realm ID ו־Refresh Token מה־OAuth Playground של Intuit ומדביקים ידנית.

אחר כך מעבירים ל־Live, לוחצים Test connection (מוצג שם החברה המחוברת), ומושכים חשבוניות מעמוד Invoices.

# חלק ב׳: תהליך הפיתוח והעלייה לאוויר

## מבנה הפרויקט

| תיקייה | מה יש בה |
|---|---|
| `src/` | אפליקציית React 19 + Vite + Tailwind v4 (הצד שהמשתמש רואה) |
| `worker/` | ה־API: Cloudflare Worker, ראוטר ידני, סשנים בעוגייה, כ־25 נקודות קצה תחת `/api/*` |
| `worker/integrations/` | המחברים החיצוניים (ACE, INTTRA, QuickBooks) |
| `worker/deckhand/` | חילוץ המזהים: הקורא הדטרמיניסטי, הקורא מבוסס המודל, אימות ISO 6346, ובניית הבלוק |
| `migrations/` | קבצי SQL לבסיס הנתונים D1 |
| `scripts/` | יצירת נתוני ההדגמה (seed) |
| `e2e/` | בדיקות Playwright מקצה לקצה |

נקודה חשובה: ה־Worker מייבא ישירות את `src/types.ts` ו־`src/data/constants.ts`, ולכן **הצד הלקוח והשרת חולקים מודל דומיין אחד**. שינוי במודל נעשה במקום אחד בלבד.

## הרצה מקומית, שלב אחרי שלב

```bash
npm install                  # התקנת חבילות (פעם אחת)
npm run db:migrate:local     # יצירת בסיס הנתונים המקומי וזריעת נתונים
npm run dev:worker           # מריץ את השרת: http://localhost:8787 (API + האפליקציה)
npm run dev                  # אופציונלי: Vite עם רענון חם על :5173, מפנה /api ל־:8787
npm run build                # בדיקת טיפוסים + בנייה
```

- לעבודה על **לוגיקה, API או אינטגרציות**: השתמשו ב־`dev:worker` בלבד (פורט 8787).
- לעבודה על **עיצוב ומסכים**: הוסיפו `npm run dev` (פורט 5173) כדי לקבל רענון מיידי.
- לאיפוס מלא של הנתונים המקומיים: `npm run db:reset:local`.

## בסיס הנתונים, כללי ברזל

1. **לעולם לא לערוך קובץ מיגרציה שכבר הורץ.** תמיד להוסיף קובץ חדש עם מספר עוקב (`0006_...sql`).
2. קובץ הזריעה `0002_seed.sql` הוא **קובץ מיוצר**, לא לערוך ידנית. ליצירה מחדש: `npm run seed:generate`. הפלט יציב וזהה בכל הרצה (מחולל אקראיות עם זרע קבוע, תאריך עוגן קבוע).
3. זריעה מחדש מחייבת מחיקה ויצירה מחדש של בסיס הנתונים.
4. **ה־CI לא מריץ מיגרציות.** אחרי שמוסיפים מיגרציה חדשה, מריצים ידנית `npm run db:migrate:remote` **לפני** שדוחפים את הקוד. אחרת המערכת בייצור תשבור.

## בדיקות

```bash
npm run db:reset:local
npm run test:e2e
# או, אם רוצים דפדפן ספציפי:
CHROMIUM_PATH=/path/to/chromium npm run test:e2e
```

הבדיקות מכסות: התחברות והתנתקות וסיסמה שגויה, חסימת כתיבה למשתמש צופה, הפרדת ארגונים (כולל חסימת גישה ישירה דרך URL ואי־גישה לחשבוניות), שמירת הגדרות, ניהול אינטגרציות (בדיקת תקינות במצב Mock, מתג כיבוי, שמירה וניקוי של מפתחות בלי דליפת סודות), זרימת החיבור ל־QuickBooks עד לשער של Intuit, משיכת חשבוניות במצב Mock, והמשכיות של הזמנה, הערה ואישור אחרי רענון.

**כלל:** לפני כל דחיפה מריצים `npm run build` (בודק טיפוסים) ואת בדיקות ה־e2e.

```
ענף חדש  →  פיתוח  →  build + בדיקות  →  commit  →  push  →  PR  →  מיזוג  →  דיפלוי אוטומטי
```

## עלייה לאוויר (Deploy)

הריפו מחובר ל־**Cloudflare Workers Builds**: כל דחיפה לענף הראשי מפעילה דיפלוי אוטומטי. אין צורך בפקודה ידנית.

- `wrangler.jsonc` מגדיר `build.command = "npm run build"`, כך ש־wrangler בונה את האפליקציה בעצמו לפני הדיפלוי.
- לדיפלוי ידני מהמחשב: `npm run deploy`.

**סדר פעולות נכון כשיש מיגרציה חדשה:**

```
1. npm run db:migrate:remote      ← קודם בסיס הנתונים
2. git push                       ← ורק אחר כך הקוד
```

אם הופכים את הסדר, המערכת החיה תרוץ מול סכימה ישנה: שמירת הגדרות QuickBooks תיכשל, עמוד החשבוניות יופיע ריק, ושאר המחברים ייפלו חזרה לברירות מחדל של Mock.

## סודות ומפתחות

```bash
cp .dev.vars.example .dev.vars              # מקומי: ממלאים ערכים, wrangler dev טוען אוטומטית
```
